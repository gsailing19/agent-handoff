# 09 — 手动接力模式（人在回路）

## 跟 Mode A/B 的区别

Mode A 和 Mode B（见 `02-usage-modes.md`）解决的是"怎么拆 Goal"的问题。本文档解决的是"拆完之后怎么跑"。

在 Mode A 中，Agent 自动串行执行 Goal，人基本是观众。在手动接力模式中，**你是编排者**——每个 Goal 跑完你审查结果，决定下一步怎么走。

## 什么时候用

| ✅ 用手动接力 | ❌ 用 Mode A（Agent 自动串行） |
|-------------|---------------------------|
| Goal 之间有未知风险，上一步结果可能影响下一步方案 | Goal 之间依赖关系清晰、方案确定 |
| 你想主动审查每步产出，确保不跑偏 | 你对方案足够自信，愿意放手让 Agent 跑 |
| 任务本身是探索性的，每步都是"先看看产出再决定" | 任务纯执行，不需要中途调整 |
| Agent 不支持原生 `/goal` 自动跨轮 | Agent 支持原生 `/goal`（Claude Code、Codex） |

一句话：**需要人在回路的质量控制时，用手动接力。**

## 操作流程

### 第 1 步：Master 出方案 + 拆分 + 预置 session-id

在 master 对话中完成三件事：

1. **设计方案**（或引用已有的方案文档）
2. **拆分 Goal 提示词**（按 `03-goal-template.md` 的六要素写）
3. **预置 session-id** — **这是最关键的一步，忘了就没法接力了**

预置 session-id 的方法：

```bash
# 在 master 对话中生成
SESSION_ID="$(date +%Y%m%d-%H%M%S)-$(uuidgen 2>/dev/null | head -c8)"
# 示例：20260604-203922-0FCD84A0
```

然后把 handoff 路径硬编码到每个 Goal 的提示词里：

```markdown
Goal 1 提示词：
  完成后写 handoff 到 .claude/agent-handoffs/20260604-203922-0FCD84A0/01-report.md

Goal 2 提示词：
  开始前读 .claude/agent-handoffs/20260604-203922-0FCD84A0/01-report.md
  完成后写 handoff 到 .claude/agent-handoffs/20260604-203922-0FCD84A0/02-report.md
```

**为什么预置很重要**：每个新对话有自己独立的 session-id，如果不预置，Goal 1 写在 `abc123/`，Goal 2 写在 `def456/`，互相找不到。预置一个共享 session-id 相当于给所有 Goal 划定一个共同的"工作区"。

### 第 2 步：开新对话，粘贴 Goal N 运行

1. 开一个全新的对话（不是继续旧对话）
2. 从 master 对话中复制 Goal N 的提示词
3. 粘贴到新对话中，回车
4. 等它跑完

新对话 = 零上下文污染。Agent 的注意力全部集中在当前 Goal，不会被前面几万行的历史拖累。

### 第 3 步：复制总结，粘贴回 master

Goal N 跑完后，Agent 会在对话里输出一段总结（handoff 文件路径 + 完成情况摘要）。把这段总结复制回 master 对话。

粘贴内容通常是：
- Handoff 文件路径（如 `.claude/agent-handoffs/20260604-203922-0FCD84A0/03-tree-report.md`）
- 完成了什么、改了什么文件
- 验证结果（tsc 零错误、grep 确认等）

### 第 4 步：Master 审查

这是人在回路的环节。Master 看总结，问自己：

- 这个 Goal 的产出符合预期吗？
- 有没有引入新问题需要后续 Goal 处理的？
- 下一个 Goal 的提示词需要调整吗？

如果发现问题，调整 Goal N+1 的提示词再放行。如果完全符合预期，直接输出原有的 Goal N+1 提示词。

### 第 5 步：重复

确认通过 → 输出 Goal N+1 提示词 → 用户复制 → 开新对话 → 粘贴运行 → 回到第 3 步。

全部 Goal 跑完后，回 master 确认一遍 handoff 目录：

```bash
ls .claude/agent-handoffs/20260604-203922-0FCD84A0/*.done
# 看到所有 *.done 文件 = 全部 Goal 顺利完成
```

## 真实案例：AgentSense UI 审计修复

- **项目**：AgentSense（Tauri 2 + React/TypeScript/Tailwind）
- **任务**：修复 UI 审计报告中的 12 个正式问题 + 3 个方法 A 发现
- **Session ID**：`20260604-203922-0FCD84A0`
- **总轮次**：4 个 Goal

### Goal 拆分

| Goal | 内容 | 文件改动 | 对话 |
|------|------|---------|------|
| Goal 1 | 统一计数逻辑 + 扫描防重入锁 + useActionItems 防御 | 6 改 + 1 新建 | 新对话 1 |
| Goal 2 | 标题栏红绿灯避让 + 状态栏截断 + 篮子图标统一 | 3 改 | 新对话 2 |
| Goal 3 | 资产树虚拟化 + 键盘导航 + 折叠/展开 + 右键菜单 | 5 改 | 新对话 3 |
| Goal 4 | 哨兵空状态按钮 + 全量审计回归验证 | 1 改 + 1 文档更新 | 新对话 4 |

### 手把手的操作记录

**Master 对话做的事情：**
1. 读取审计报告 `docs/agentsense-ui-audit.md`，梳理出 15 项待修复问题
2. 按优先级和依赖关系拆成 4 个 Goal（P1 先修、P2 其次、P3 最后）
3. 生成 session-id `20260604-203922-0FCD84A0`
4. 每个 Goal 提示词中硬编码了 handoff 路径
5. 每个 Goal 跑完后审查总结，确认通过后输出下一个

**新对话做的事情（每个 Goal）：**
1. 只拿到一个 Goal 的提示词（约 2000 字符）
2. 按提示词中指定的路径读取上游 handoff 文件获取上下文
3. 实现任务、跑验证命令、写 handoff
4. 输出一句话总结

### 为什么选了手动接力而不是 Mode A

这次修复有不确定性——15 个问题分散在 10+ 个文件中，P2-2 "重新扫描无响应"的根因在跑 Goal 1 之前只是猜测。如果在 Mode A 中 Agent 自动串行，Goal 1 跑偏了，Goal 2-4 全浪费。手动接力让你在每一步确认"方向对了"，再放行下一步。

## 常见问题

**Q: 这和直接在一个对话里串行跑有什么区别？**
A: 在一个对话里跑 4 个 Goal，到 Goal 3 时对话历史已经几万行，Agent 会开始混淆早期决策、重复修改已改过的文件。手动接力每个 Goal 只有 1000-3000 行的上下文，注意力集中。

**Q: 粘贴回去会不会出错？**
A: 有两个保险：1) handoff 文件是结构化的，即使粘贴内容漏了细节，下游 Goal 的 Agent 会自己去读 handoff 文件；2) master 的审查只确认"方向对不对"，不依赖粘贴内容的完整性。

**Q: 如果在 Goal 3 发现 Goal 1 的东西需要改怎么办？**
A: 这正是手动接力的优势。因为 master 看完了 Goal 1-3 的所有总结，能判断是否需要开一个增量 Goal 5 来修，还是把修订塞进 Goal 4。这在 Mode A 里很难处理——Agent 不知道要不要"回头修"。
